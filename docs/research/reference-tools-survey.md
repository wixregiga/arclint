# Reference Tools Survey: steiger, ls-lint, golangci-lint, grule, expr/CEL

Research report, 2026-08-10, for the arclint multi-language design. All claims sourced directly from fetched repo READMEs, doc source files, or GitHub issues/discussions — no secondhand summaries. `(same source)` refers to the immediately preceding citation. [INFERENCE] labels mark statements not directly verified.

## 1. Steiger (feature-sliced/steiger)

Rules live inside plugins built with `createPlugin` from `@steiger/toolkit`, a compile-time-only identity function typed `Plugin<Context, Rules>` ([create-plugin.ts](https://raw.githubusercontent.com/feature-sliced/steiger/master/packages/toolkit/src/create-plugin.ts)). A rule is a plain object: `{ name, check(this: Context, root: Folder, ruleOptions) => RuleResult }` ([packages/types/index.ts](https://raw.githubusercontent.com/feature-sliced/steiger/master/packages/types/index.ts)). `check` receives a plain recursive tree: `File = { type: 'file', path }`, `Folder = { type: 'folder', path, children: Array<File|Folder> }` (same source). It returns `{ diagnostics: PartialDiagnostic[] }`, each `{ message, fixes?, location }`; the core adds `ruleName`, `severity`, and `getRuleDescriptionUrl` (same source). Cross-rule state (import resolution, dependency graphs, language detection) sits in "services" subscribed to VFS-change events, cached per FSD root ([discussion #107](https://github.com/feature-sliced/steiger/discussions/107)). Config is `steiger.config.ts/.js` via cosmiconfig, ESLint-flat-config style: `defineConfig([...fsd.configs.recommended, { files, ignores, rules }])` ([README](https://raw.githubusercontent.com/feature-sliced/steiger/master/README.md)). Only one plugin exists, `@feature-sliced/steiger-plugin`; the README states: "Currently, Steiger is not extendable with more rules, though that will change in the near future" (same source) — not yet a supported third-party path despite generic type contracts in source. A GitHub discussion mentions a `createRule` helper in the toolkit; current [index.ts](https://raw.githubusercontent.com/feature-sliced/steiger/master/packages/toolkit/src/index.ts) exports no such function — rules appear to be plain object literals against `Rule` instead.

## 2. ls-lint (loeffel-io/ls-lint)

Config is `.ls-lint.yml`, keyed by directory glob under `ls:`, e.g. `ls: { packages/*/src: { .js: kebab-case, .ts: camelCase | PascalCase } }` ([README](https://github.com/loeffel-io/ls-lint)). The rule vocabulary is closed: named-case rules (kebab-case, camelCase, PascalCase, snake_case), `regex:<pattern>`, and `exists:<n>`, combinable with `|` for "any of" (same source). It expresses naming/existence on paths only, nothing about file contents or import graphs, and docs show no plugin or custom-function mechanism ([ls-lint.org](https://ls-lint.org/)). Written in Go; ships as native binaries for Windows/macOS/Linux plus an npm wrapper, Homebrew formula, Docker image, and GitHub Action ([README](https://github.com/loeffel-io/ls-lint); [ls-lint.org](https://ls-lint.org/)) — one static binary, fixed vocabulary, no extensibility story.

## 3. golangci-lint — two plugin systems

**Go plugin (.so)**: a plugin's main package exports `func New(conf any) ([]*analysis.Analyzer, error)`, built with `go build -buildmode=plugin`, registered under `linters-settings.custom.<name>: { path: /example.so, settings: {...} }` ([go-plugins.mdx](https://raw.githubusercontent.com/golangci/golangci-lint/master/docs/src/docs/plugins/go-plugins.mdx)). Go's plugin package forces exact build parity: "the plugin as well as the golangci-lint binary needs to be built for the same environment," and "All versions of libraries that overlap golangci-lint MUST be set to the same version as golangci-lint" (same source) — consumers typically rebuild golangci-lint locally (`CGO_ENABLED=1 make build`) to match.

**Module plugin system**: a `.custom-gcl.yml` manifest lists plugins by import path/version or local path; `golangci-lint custom` clones golangci-lint at a pinned version, injects the plugin imports, and compiles one static custom binary, needing only Go and git ([module-plugins.mdx](https://raw.githubusercontent.com/golangci/golangci-lint/master/docs/src/docs/plugins/module-plugins.mdx)). Registration reuses `linters-settings.custom`, with `type: "module"` (same source). [INFERENCE] Compiling from source into one binary, instead of loading dynamically, sidesteps the .so system's exact-version/environment coupling — inferred from the constraints above; neither doc states a rationale.

Source note: citations point to the raw GitHub `.mdx` sources rather than the rendered `golangci-lint.run` pages because the rendered pages returned no fetchable content (JS-rendered Docusaurus site); the `.mdx` files are the same docs' source of truth.

## 4. grule (hyperjumptech/grule-rule-engine)

GRL example: `rule SpeedUp salience 10 { when TestCar.SpeedUp == true && TestCar.Speed < TestCar.MaxSpeed then TestCar.Speed = TestCar.Speed + TestCar.SpeedIncrement; }` ([README](https://raw.githubusercontent.com/hyperjumptech/grule-rule-engine/master/README.md)). Facts are Go structs in a DataContext; rules forward-chain, ordered by salience. "Some form of the RETE algorithm was implemented starting from version 1.1.0," replacing naive re-evaluation, caching expression sub-nodes in working memory until a referenced variable changes ([RETE_en.md](https://raw.githubusercontent.com/hyperjumptech/grule-rule-engine/master/docs/en/RETE_en.md)). Same doc's real limitation: the engine cannot see mutations from external function/method calls on a fact, so authors must call `Changed()` manually (same source). The README calls production rule systems generically "Turing complete" (same source) — a claim about the class, not a benchmarked Grule property. Tracker friction: issue [#463](https://github.com/hyperjumptech/grule-rule-engine/issues/463) (Sep 2024) — "the lack of recent activity is a little alarming" — unanswered by maintainers, despite v1.20.4 shipping Aug 2025 ([pkg.go.dev](https://pkg.go.dev/github.com/hyperjumptech/grule-rule-engine)); other open issues cover a missing NOT operator ([#94](https://github.com/hyperjumptech/grule-rule-engine/issues/94)), map/slice gaps ([#41](https://github.com/hyperjumptech/grule-rule-engine/issues/41)), and max-cycle behavior ([#108](https://github.com/hyperjumptech/grule-rule-engine/issues/108)).

[INFERENCE] A forward-chaining engine with salience and mutable working memory solves a different problem than architecture linting: linter rules are pure, stateless predicates over one static tree, evaluated once per file, with no rule needing to re-trigger another. Grule's core value — inference chains where firing one rule changes facts that re-fire others — is unneeded machinery here, and its string-authored DRL surfaces type errors only at runtime. Wrong tool class for this job.

## 5. expr vs CEL

`expr.Compile(code, expr.Env(StructType{}))` type-checks field/method access against a real Go struct at compile time, rejecting mismatches before evaluation ([README](https://raw.githubusercontent.com/expr-lang/expr/master/README.md)). Expr claims three safety properties — memory-safe, side-effect-free, always-terminating — plus an optimizing compiler and bytecode VM, benchmarked against other engines via a linked comparison (same source). Listed adopters: Google Cloud Platform, Uber, GoDaddy, ByteDance, Alibaba, Argo, CrowdSec, CoreDNS, OpenTelemetry Collector (same source). CEL (google/cel-go, spec at google/cel-spec) is explicitly "non-Turing complete," evaluating "in linear time" and "mutation free" — a constraint the spec says makes it "orders of magnitude faster than equivalently sandboxed JavaScript," staying embeddable via host-supplied functions/variables ([cel-spec README](https://raw.githubusercontent.com/google/cel-spec/master/README.md)). Kubernetes uses CEL in ValidatingAdmissionPolicy, GA since v1.30, where `spec.validations` holds CEL expressions evaluated against the admission request ([kubernetes.io](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)).

[INFERENCE] Expr fits a Go linter better: it type-checks directly against native Go structs via reflection, giving rule authors real Folder/Diagnostic types with no adapter layer. CEL's type system centers on protobuf/JSON-like values needing explicit registration to expose Go structs — a cost worth paying only when expressions must be portable across non-Go hosts or stored as long-lived policy, not typical for a single-binary linter.

## Lessons for a pluggable Go linter

- **Prefer compile-time plugin composition over dynamic loading**: golangci-lint's .so route forces exact library/environment parity between host and plugin ([go-plugins.mdx](https://raw.githubusercontent.com/golangci/golangci-lint/master/docs/src/docs/plugins/go-plugins.mdx)); its module system compiles one binary per user from source instead ([module-plugins.mdx](https://raw.githubusercontent.com/golangci/golangci-lint/master/docs/src/docs/plugins/module-plugins.mdx)) — the same tradeoff applies to any Go linter with native-code plugins.
- **Separate the rule contract from the traversal engine**: Steiger's `Rule = { name, check(root, options) => { diagnostics } }` over a plain recursive Folder/File tree ([types/index.ts](https://raw.githubusercontent.com/feature-sliced/steiger/master/packages/types/index.ts)) is a minimal, serializable contract that hides filesystem/caching internals from rule authors — worth copying in any language.
- **Keep naming/path rules declarative, outside any general-purpose language**: ls-lint's closed YAML vocabulary covers most naming conventions with no plugin system at all ([README](https://github.com/loeffel-io/ls-lint)). Save a real expression language for predicates needing actual logic, like import-boundary checks.
- **For those predicates, a typed, terminating expression language embedded against the linter's own Go types (expr's model) beats a forward-chaining engine or a protobuf-oriented policy language**: linter checks are single-pass predicates, not inference chains needing salience, and gain more from compile-time struct checks than cross-host portability.
- **Do not advertise third-party extensibility before the internal contract is stable**: Steiger already has generic Plugin/Rule types in source ([create-plugin.ts](https://raw.githubusercontent.com/feature-sliced/steiger/master/packages/toolkit/src/create-plugin.ts)), yet its README still says it is not extendable by third parties ([README](https://raw.githubusercontent.com/feature-sliced/steiger/master/README.md)) — a type contract existing is necessary but not sufficient for a supported plugin API.
