# Multi-Language Rule Engines and Single-Binary Analysis Options

Research report, 2026-08-10, for the arclint multi-language design. Every claim carries its source link inline; [INFERENCE] labels mark statements not directly verified.

## 1. ast-grep — declarative multi-language rules in one Rust binary

**Rule file schema** ([reference/yaml](https://ast-grep.github.io/reference/yaml.html)): `id`, `language`, `rule`, `constraints` ("Additional meta variables pattern to filter matches"), `utils` ("A dictionary of utility rules that can be used in `matches` locally"), `transform`, `fix`, `rewriters`, `severity`, `message`, `note`, `labels`, `files`, `ignores`, `url`, `metadata`.

**Rule grammar** ([reference/rule](https://ast-grep.github.io/reference/rule.html)): atomic — `pattern`, `kind`, `regex`, `nthChild`, `range`; relational — `inside`, `has`, `precedes`, `follows`, all accepting `stopBy` (`neighbor` | `end` | a rule) and `inside`/`has` also accepting `field`; composite — `all`, `any`, `not`, `matches`. `matches` is the only way to reference a util. `kind` names are raw tree-sitter node types ([atomic-rule](https://ast-grep.github.io/guide/rule-config/atomic-rule.html)). Utils are either a local `utils:` dict (file-scoped, same language) or global files under `utilDirs`; self-reference via `has`/`inside` is allowed but "Dependency Cycle is not allowed" ([utility-rule](https://ast-grep.github.io/guide/rule-config/utility-rule.html)).

**Built-in languages**: 34, each with CLI aliases and extensions ([reference/languages](https://ast-grep.github.io/reference/languages.html)).

**How it stays one binary**: `crates/language/Cargo.toml` lists ~27 optional `tree-sitter-*` grammar crates gated behind a `builtin-parser` feature that is on by `default` ([Cargo.toml](https://raw.githubusercontent.com/ast-grep/ast-grep/main/crates/language/Cargo.toml)). Each grammar crate's `build.rs` compiles `parser.c`/`scanner.c` with the `cc` crate into a static lib linked into the executable ([tree-sitter-go build.rs](https://raw.githubusercontent.com/tree-sitter/tree-sitter-go/master/bindings/rust/build.rs)). Cost: Arch `ast-grep 0.44.1` is 5.4 MB compressed / **48.7 MB installed** ([archlinux.org](https://archlinux.org/packages/extra/x86_64/ast-grep/)).

**Custom languages break the single-binary property.** You compile a grammar with `tree-sitter build --output lang.so` and register it under `customLanguages` with `libraryPath` (string or per-platform map), `extensions`, `expandoChar`, `languageSymbol`, `outlineRules` ([custom-language](https://ast-grep.github.io/advanced/custom-language.html), [sgconfig reference](https://ast-grep.github.io/reference/sgconfig.html)). That is `dlopen` of a per-OS `.so`/`.dylib`/`.dll` — you now ship N+1 artifacts. `sgconfig.yml` also carries `ruleDirs`, `utilDirs`, `testConfigs`, `languageGlobs`, and experimental `languageInjections`.

## 2. semgrep — why it is not a small binary

A rule requires `id`, `message`, `severity`, `languages` (an **array**, so one rule can target several languages) and exactly one of `pattern`/`patterns`/`pattern-either`/`pattern-regex`, composed with `pattern-inside`, `pattern-not`, `metavariable-regex`, `focus-metavariable` ([rule syntax](https://docs.semgrep.dev/writing-rules/rule-syntax)). Patterns are written in the target language's own concrete syntax and all languages are normalized to one shared IR — "It has a generic AST, defined in `AST_generic.ml`" — fed by `ocaml-tree-sitter` grammars plus legacy Menhir/pfff parsers for Python/PHP/OCaml ([semgrep-core contributing](https://docs.semgrep.dev/contributing/semgrep-core-contributing)). It is two programs, not one: "`semgrep-core` is called by default with `-config`" as a subprocess by the Python CLI, returning JSON built in `JSON_report.ml` (same page), and OSS distribution is `pipx install semgrep` / `uv tool install semgrep` / Docker, with no standalone binary documented ([OSS deployment](https://docs.semgrep.dev/deployment/oss-deployment)). The `osemgrep` effort reimplements the Python CLI in OCaml to merge both into one binary ([DeepWiki, secondary source](https://deepwiki.com/semgrep/semgrep/2-core-architecture)).

## 3. tree-sitter from Go

**(a) cgo bindings.** `tree-sitter/go-tree-sitter` ships nothing by default — "By default, none of the grammars are included in this package"; each grammar is a separate `go get` ([README](https://github.com/tree-sitter/go-tree-sitter)). It is cgo: install docs state you need "A C compiler (required for CGO compilation)" and `export CGO_ENABLED=1` ([DeepWiki install](https://deepwiki.com/tree-sitter/go-tree-sitter/1.1-installation-and-setup)); the README warns "Due to bugs with `runtime.SetFinalizer` and CGO, you must always call `Close`". `smacker/go-tree-sitter` vendors ~30 grammars' C sources in-repo, 562 stars, **not** archived ([repo](https://github.com/smacker/go-tree-sitter)), with a Windows cross-build failure filed and closed without a documented fix ([issue #120](https://github.com/smacker/go-tree-sitter/issues/120)). Consequences: `CGO_ENABLED=0` is impossible, each `GOOS/GOARCH` needs its own C cross-toolchain, and a fully static build needs musl. Size scales with grammar count — `alexaandru/go-sitter-forest` (~490 parsers) warns "beware, your binary size **will be huge**, as in 350MB+ huge" and offers standalone/plugin subsetting ([repo](https://github.com/alexaandru/go-sitter-forest)).

A middle route: the official README notes grammars "can be loaded at runtime from a shared library via purego". But purego "requires dynamic linking — the target library must be available as a shared object at runtime... making static linking incompatible", Tier 1 being Linux/macOS/Windows/Android/iOS on amd64/arm64 ([purego](https://github.com/ebitengine/purego)). That trades cgo for shipping `.so` files, i.e. ast-grep's custom-language problem.

**(b) WASM / pure Go.** Grammars compile to `.wasm` via `tree-sitter build --wasm` using the WASI SDK ([CLI build docs](https://tree-sitter.github.io/tree-sitter/cli/build.html)). The one Go wazero wrapper found, `malivvan/tree-sitter`, self-describes as "pre release software so expect bugs", has **5 stars and a single push on 2025-01-25** ([repo](https://github.com/malivvan/tree-sitter), [API](https://api.github.com/repos/malivvan/tree-sitter)) — effectively abandoned. The live option is `odvcencio/gotreesitter`, a pure-Go reimplementation of the runtime: no cgo, 206 embedded grammars as compressed blobs (~24 MB with all embedded), build tags `grammar_set_core` / `grammar_subset` / `grammar_blobs_external`, cross-compiles to any `GOOS/GOARCH` including `wasip1` ([repo](https://github.com/odvcencio/gotreesitter), [pkg.go.dev](https://pkg.go.dev/github.com/drummonds/gotreesitter)).

Honest caveats on gotreesitter: created **2026-02-20**, 551 stars, pushed today ([API](https://api.github.com/repos/odvcencio/gotreesitter)) — six months old. Its own README says earlier synthetic benchmarks "were withdrawn" and puts full parsing at **~3.9–4.85x slower than C**. The pkg.go.dev path `drummonds/gotreesitter` is a **0-star stale fork** of it ([API](https://api.github.com/repos/drummonds/gotreesitter)). Fidelity risk is real: many grammars need hand-written C `scanner.c` (Python indent/dedent, Bash and Ruby heredocs) ([external scanners](https://tree-sitter.github.io/tree-sitter/creating-parsers/4-external-scanners.html)), and gotreesitter re-implements 119 of them in Go, claiming 203/206 grammars parse error-free. The only third-party usage report found is one blog post (binary 12 MB to 32 MB, 83 ms for 66 Go files) ([dev.to](https://dev.to/thegdsks/parsing-11-languages-in-pure-go-without-cgo-how-i-replaced-regex-with-a-tree-sitter-runtime-g04)). **[INFERENCE]** No evidence of large-scale production deployment exists for either the WASM or pure-Go route.

## 4. Cheap import extraction

**GitHub's dependency graph parses manifests and lockfiles only** — the supported-ecosystems table lists `package-lock.json`, `go.mod`, `requirements.txt`, `Cargo.lock` etc., and no source-file extension appears anywhere in it ([concepts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-graph), [supported ecosystems](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/dependency-graph-supported-package-ecosystems)). It does no source-level import extraction.

**tach** uses a real parser, not regex: its `Cargo.toml` depends on `ruff_python_ast` and `ruff_python_parser` ([Cargo.toml](https://github.com/gauge-sh/tach/blob/main/Cargo.toml)), and its FAQ states "Tach uses the AST to find imports and public members, and dynamic imports (using a string path) and dynamic names... are not supported" ([FAQ](https://docs.gauge.sh/usage/faq/)). Imports match dotted `path =` module declarations resolved against `source_roots` ([tach.toml](https://github.com/tach-org/tach/blob/main/tach.toml)).

**dependency-cruiser** uses `acorn`/`acorn-jsx`, `tsc`, optionally `swc`, plus `enhanced-resolve` for Node semantics; fully variable `require(someVariable)` / `import(someOtherVariable)` do not resolve because it "focuses on doing static analysis only" ([FAQ](https://github.com/sverweij/dependency-cruiser/blob/main/doc/faq.md)). `export * from` is a modeled dependency type and TS aliases surface as `aliased-tsconfig-paths` ([rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)).

**Where regex breaks, by grammar.** Go: `ImportPath = string_lit` — always literal, never computed — and `ImportDecl` sits outside `TopLevelDecl`, so function-scoped imports do not exist ([Go spec: imports](https://go.dev/ref/spec#Import_declarations), [source file organization](https://go.dev/ref/spec#Source_file_organization)); the only trap is the grouped `import ( ... )` block, which defeats a `^import "` anchor. Python: `import_stmt` is a `simple_stmt` legal inside any function or conditional, with a parenthesized multi-line form ([grammar](https://docs.python.org/3/reference/simple_stmts.html#the-import-statement)), and `importlib.import_module(name)` is textually indistinguishable from any other call ([docs](https://docs.python.org/3/library/importlib.html)); PEP 420 namespace packages break path-to-module mapping ([PEP 420](https://peps.python.org/pep-0420/)). JS/TS: webpack itself concedes "it is not possible to use a fully dynamic import statement, such as `import(foo)`" ([webpack](https://webpack.js.org/api/module-methods/#magic-comments)); `import type` and `paths`/`baseUrl` change classification without changing lexical shape.

**Assessment for "no third-party imports in `internal/entities/`"**: **[INFERENCE]** For **Go**, a lexer-grade extractor is sufficient — the grammar structurally forecloses computed and function-scoped imports; the only correctness work is comment/string stripping and handling both import forms. Better still, Go needs no regex at all: `go/parser` has an `ImportsOnly` mode, "stop parsing after import declarations" ([pkg.go.dev/go/parser](https://pkg.go.dev/go/parser)), which is exact and stdlib-cheap. For **Python** and **JS/TS** regex is not reliable, because the failure mode is a *false negative* (`importlib.import_module("boto3")`, `require(name)`) — an undetected violation, which is strictly worse for an enforcement rule than a false positive a human can dismiss. Syntactic variety (`export * from`, grouped imports, `import type`) is tractable; computed specifiers are not.

## 5. Cross-file consistency rules

**No surveyed tool has a declarative primitive for "every file matching X must have a corresponding entry in a set derived from Y."**

- **ArchUnit** is programmatic Java. `ArchCondition<T>` exposes `init(Collection<T> allObjectsToTest)` — called once with the whole collection — plus per-item `check()` ([ArchCondition.java](https://github.com/TNG/ArchUnit/blob/main/archunit/src/main/java/com/tngtech/archunit/lang/ArchCondition.java)), so a set-difference is expressible, but only as hand-written Java; `ClassesTransformer` + `ArchRuleDefinition.all(...)` generalize the input collection ([user guide](https://www.archunit.org/userguide/html/000_Index.html)).
- **Nx conformance** rules are TypeScript modules referenced by path in `nx.json`, not YAML: `createConformanceRule({ implementation: async (context) => ... })` with `context.projectGraph` giving whole-workspace visibility ([create-conformance-rule](https://nx.dev/docs/reference/conformance/create-conformance-rule)). Code, not config.
- **Semgrep cannot express it.** Community Edition "can only analyze interactions within a single function" ([Pro engine intro](https://docs.semgrep.dev/semgrep-code/semgrep-pro-engine-intro)); `join` mode is labeled experimental and not actively maintained, and its only operators are `==`, `!=`, `<`, `>` — no set-difference ([join mode](https://docs.semgrep.dev/experiments/join-mode/overview)); interfile dataflow is a paid Pro capability (Pro engine intro).
- **danger-js** can, as arbitrary JS: `danger.git.created_files` ([reference](https://danger.systems/js/reference.html)) plus direct `fs.readFileSync` as shown in the official dependencies tutorial ([tutorial](https://danger.systems/js/tutorials/dependencies.html)). Issue #431, "Provide primitives for 'if this file exists, then so should this' sort of rules", is the exact request — still unimplemented ([#431](https://github.com/danger/danger-js/issues/431)).
- **Closest declarative fit** is dependency-cruiser's `required` rule type, which asserts a module matcher has at least one edge to a `to` matcher ([rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)) — but "Y" is always an *import edge*, never an arbitrary content-derived set. Same shape in `eslint-plugin-boundaries` `element-types` ([docs](https://github.com/javierbrea/eslint-plugin-boundaries/blob/master/docs/rules/element-types.md)), go-arch-lint ([repo](https://github.com/fe3dback/go-arch-lint)), arch-go ([repo](https://github.com/arch-go/arch-go)). Konsist and NetArchTest are ArchUnit-shaped programmatic DSLs ([Konsist](https://docs.konsist.lemonappdev.com/), [NetArchTest](https://github.com/BenMorris/NetArchTest)). ast-grep's utils reuse rule *fragments* but do not aggregate matches across files ([utility-rule](https://ast-grep.github.io/guide/rule-config/utility-rule.html)); **[INFERENCE]** no cross-file aggregation appears in its docs.

So `internal/entities/*_{substrate}.go` matching substrates in `internal/setup/**/*.go` is, in every existing tool, imperative code — and is therefore **a genuine gap a declarative YAML linter could fill**.

## Viable paths for a Go single-binary polyglot linter, ranked

1. **Tiered extraction: exact native parsers where they are free, tree-sitter only where needed.** Use `go/parser` with `ImportsOnly` for Go (stdlib, exact, zero size cost) and add tree-sitter only for languages with no Go-native parser. Lowest risk; keeps the binary small; matches the finding that the rule classes that matter (import boundaries, cross-file correspondence) rarely need full ASTs.
2. **gotreesitter with `grammar_subset`.** Only route that preserves `CGO_ENABLED=0`, cross-compilation, and one static binary while giving real ASTs. Cost: ~4x slower parsing, per-grammar fidelity risk from re-implemented external scanners, and a six-month-old single-maintainer dependency. **[INFERENCE]** Acceptable if you pin the version, embed 5-10 grammars rather than 206, and treat parse failures as skip-not-crash.
3. **cgo (`tree-sitter/go-tree-sitter` + selected grammar modules).** Best parser fidelity and speed, and the only route with production track record — but it forfeits the premise: you need a C cross-toolchain per target, cannot set `CGO_ENABLED=0`, and need musl for a static build.
4. **Dynamic grammar loading (purego, or ast-grep-style `.so`).** Rejected for this goal: purego explicitly cannot static-link, so you ship a binary plus per-OS shared objects.
5. **WASM grammars via wazero.** Architecturally clean and cgo-free, but the only Go wrapper found is 5 stars and untouched since January 2025. **[INFERENCE]** Not currently a maintained path; would mean writing and owning the host layer yourself.

**Rule-language recommendation**: borrow ast-grep's shape — `rule` with atomic/relational/composite operators, `utils` + `matches` for reuse, `files`/`ignores` globs — since it is proven declarative and language-agnostic. But neither ast-grep nor semgrep gives you Section 5's correspondence rule, so that operator (a declarative set-difference between two file-derived capture sets) has no prior art to copy and must be designed.
